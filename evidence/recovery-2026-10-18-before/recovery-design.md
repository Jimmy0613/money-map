# 복원 차단 상세 설계

2026-09-25. 요구사항 근거: architecture11절, FR-028, NFR-009. **설계 완료 / 아래 운영 제어 계층은 아직 구현·운영 검증 전**이다. 현재 restore-public.py와 APP_RECOVERY_REQUIRED는 격리 훈련용 부분 구현이며 본 설계 전체를 충족하지 않는다. 승인된 삭제/최신성/보존 기준은 변경하지 않는다.

## 신뢰 경계와 책임

| 책임 | 담당 | 결정 근거 |
|---|---|---|
| 사용자·거래·ledger 원자적 삭제 | Backend/PostgreSQL | 기존 트랜잭션 유지 |
| 정상/복원 배포 식별 및 현재 복원 세대 | 운영 제어 저장소 | 사용자 DB/public/privacy 백업과 분리; 단조 증가 세대, 접근 제어·변경 감사 |
| 최신 확정 삭제를 포함한 WAL 확보 | WAL 보존/독립 복제 저장소 | DB system identifier·timeline·복원 목표 LSN 및 WAL 연속성 검증 |
| 복원 작업과 검증 결과 | 복원 실행기 | 격리된 새 대상만 생성, 사용자 DB 직접 초기화 금지 |
| 외부 트래픽 개방 | 배포 제어기/ingress | 외부 제어 저장소의 현재 상태·대상 결합을 확인해야만 연결 |
| API 접근 차단 | Backend recovery gate | production에서는 필수 증거 누락·위조·만료·대상 불일치 시 fail closed |

외부 저장소의 구체 제품은 무료 운영 환경 선정 후 결정한다. 무료로 위 신뢰 경계를 충족할 수 없다면 요구사항을 조용히 완화하지 않고 배포를 보류한다. 서명키/저장소 권한은 서비스 DB 접근 권한과 분리한다. 같은 과거 DB 백업 안의 플래그·해시·인증서만으로 최신성을 증명하지 않는다.

## 상태와 전이

`UNREGISTERED → BLOCKED → FENCED → LEDGER_VERIFIED → RESTORED → RECONCILED → VALIDATED → RELEASED`

- UNREGISTERED: 기본 상태. 운영 환경의 미등록 DB/새 배포도 외부 접근 불가. 신규 빈 DB는 복원과 별도인 bootstrap 절차에서 최초 세대를 등록한다. 자동 false 기본값으로 우회하지 않는다.
- BLOCKED: 복원 세대를 외부 저장소에 생성하고 ingress 차단. 애플리케이션 로그인/refresh/개인 API 및 readiness503, liveness만 허용.
- FENCED: 모든 쓰기 주체와 세션을 차단하고, 다른 배포/작업자의 쓰기 중단을 확인. 확인 불가하면 진행 금지. 처리 중인 삭제 commit도 목표 지점에 포함한다.
- LEDGER_VERIFIED: 독립 복제/WAL을 통해 최신 확정 삭제를 포함한 목표 지점까지 회복한 ledger의 증거를 검증한다. 해시는 내용 무결성만 확인한다.
- RESTORED: 새 대상에 public만 복원한다. 검증된 privacy를 과거 public 백업으로 덮어쓰지 않는다.
- RECONCILED: ledger 사용자 재삭제, 소유권/참조 고아 검사, 모든 인증 세션·refresh 폐기를 원자적으로 수행한다. 중간 실패는 접근 차단 상태로 남고 재개 시 동일 세대로 재검증한다.
- VALIDATED: 스키마/Migration 호환성, 대상 DB 결합, 재삭제 결과·세션0·무고아 결과를 기록한다. 이 상태만으로 외부 개방하지 않는다.
- RELEASED: 외부 저장소의 최신 세대/대상/목표 지점과 결과가 일치할 때 배포 제어기가 개방 증거를 발급하고 ingress와 Backend gate가 각각 확인한다. 새 복원 시작은 세대를 올려 이전 증거를 무효화한다.

모든 오류는 BLOCKED로 처리한다. 상태 변경은 현재 세대에 대한 compare-and-set과 단일 작업자 lease로 수행한다. 프로세스 재시작이나 DB 스냅샷 롤백으로 상태가 RELEASED로 되돌아가지 않도록 상태의 권위는 외부 저장소에 둔다.

## 최신성 증거

증거에는 환경/배포 ID, 복원 세대, 대상 DB 인스턴스 ID, 원본 DB system identifier, timeline 이력, 목표 WAL LSN, 연속 WAL 구간 검증 결과, ledger digest, 검증 실행 ID, 발급/만료 시각과 서명 식별자를 결합한다. 개인정보·이메일·위치·비밀번호는 넣지 않는다.

원본이 살아 있으면 모든 쓰기를 멈춘 뒤 외부 제어기가 목표 WAL 지점을 고정하고 독립 복제/보존본이 그 지점까지 따라잡았음을 확인한다. 원본 유실 시에는 DB와 독립된 최신 commit 보전 근거가 필요하다. 삭제 성공 응답 이후의 commit 유실이 없도록 동기 WAL 보전 등 내구성 정책이 먼저 검증되어야 한다. 단순 비동기 아카이브나 '가장 최근 파일' 추정만으로 이를 충족했다고 처리하지 않는다. 최신 확정 commit의 경계를 증명할 수 없으면 복구 가능한 범위의 데이터 확인만 하고 공개하지 않는다.

서명 검증만으로 최신성을 인정하지 않는다. 서명된 오래된 증거도 외부 저장소의 현재 세대/대상/목표와 일치하지 않으면 거부한다. timeline이 다른 LSN은 숫자만 비교하지 않고 계보를 검증한다. 외부 권위 저장소 접근 실패나 증거 만료 시 gate와 ingress 모두 차단한다. 재삭제 검증 이후 대상 DB가 교체되면 증거 결합이 깨져 다시 검증해야 한다.

## 배포 강제

운영에서는 복원 검증/정상 신규 bootstrap으로 등록된 배포만 네트워크에 연결한다. Backend는 유효한 개방 증거를 필수로 요구하고, 플래그 누락·APP_RECOVERY_REQUIRED=false만으로 열리지 않게 한다. Backend 직접 포트도 외부로 노출하지 않는다. local 프로필 예외는 loopback/격리 네트워크에 한정하고 운영 origin/ingress와 함께 사용할 수 없도록 검사한다. 이 기능 구현 전에는 현재 임시 휴대폰 환경을 운영 완료로 승격하지 않는다.

세션 폐기 전·후 실제 로그인/refresh 및 과거 access token 시도를 수행한다. DB 복원이나 검증 결과 생성만으로 통과하지 않고 ingress를 통한 HTTP 차단도 확인한다. 개방 시점은 검증 결과와 동일한 세대/대상에 대한 원자적 배포 결정으로 묶어 검증과 개방 사이 DB 변경을 차단한다.

## 수락 시나리오

| ID | 시나리오 | 필수 결과 | 현재 상태 |
|---|---|---|---|
| REC-01 | 설정·증거 없이 운영 시작 | readiness/API503, 외부 공개 불가 | 설계됨 / 구현·실행 전 |
| REC-02 | 오래된 ledger에 올바른 hash/서명 | 현재 외부 목표/세대 불일치로 차단 | 격리 후보 공개 불허만 검증; 운영 gate 미구현 |
| REC-03 | 외부 권위 저장소 유실/접속 실패/만료 | 자동 개방·무제한 캐시 사용 금지 | 설계됨 / 구현·실행 전 |
| REC-04 | 전체 DB와 로컬 설정을 과거로 복원 | 외부 최신 세대와 대조하여 차단 | 설계됨 / 구현·실행 전 |
| REC-05 | 목표까지 WAL 공백/다른 timeline | 최신성 미확인으로 차단 | 설계됨 / 구현·실행 전 |
| REC-06 | 재삭제·고아 검사·세션 폐기 실패 또는 중단 | rollback/차단 유지; 재시작도 공개 금지 | 일부 격리 훈련만 검증 |
| REC-07 | 검증 뒤 대상 DB 교체/세대 증가 | 이전 개방 증거 무효 | 설계됨 / 구현·실행 전 |
| REC-08 | 최신 증거와 동일 대상의 전체 절차 성공 | 삭제 사용자 부재·생존 데이터 유지·과거 세션 거부 후 개방 | 운영 실행 전 |

원본71개 테스트 사례를 대체하지 않고 위 하위 시나리오로 보완한다. 암호화·최대30일 보존과 ledger 정리의 복원 지점 만료 증거도 운영 완료 조건으로 유지한다. 현재 제품 코드에 이 운영 제어 계층이 구현됐다고 보고하지 않는다.
